# 人が編集できる計画レビューの引き継ぎ

Codex → Claude Code と Claude Code → Codex のどちらでも、依頼元を「作成元」、相手を「レビュアー」と呼ぶ。計画を判断する役割と、依頼文・結果を転送する操作を分ける。

## 呼び出し

Codex は `$plan-review-handoff`、Claude Code は `/plan-review-handoff` に、用途と対象を添える。用途は独自 CLI の引数ではなく依頼文の一部である。

- `prepare`: 「この計画を相手に渡す依頼文を用意して」
- `review`: 「受け取った計画を元の依頼と照合してレビューして」
- `assess`: 「戻った指摘の採否を判断して計画へ反映して」

ユーザーが人を介した往復を選んだときに使う。通常の計画作成を無条件にこのフローへ切り替えない。出力は原則チャット本文とし、ファイルへの保存は依頼と現在のモードが許す場合に行う。

## 共通の境界

- 作成元が元の依頼・関連コードを調べ、意図を対話で明確にする。ユーザーに文脈の要約を任せない。
- 依頼文と結果の両方を、ユーザーが編集・追記・変更せず転送できる形にする。各出力の後は転送待ちで止める。
- この手動フローから相手 CLI・サブエージェントを自動起動せず、自動送信・受信監視・agmsg の自動参加も行わない。ユーザーが明示した転送手段の権限・承認は維持する。
- 認証情報・不要な個人情報・会話の生ログを引き継がない。モデル ID は当該セッションで開示されたものだけを記し、設定や別セッションから推測しない。不明は不明とする。
- レビュー専任の依頼では必要なコード・公式資料・Skill の調査を許可し、編集（計画ファイル作成を含む）・実装・共有リソース変更・再委譲を禁止する。変更・委譲を伴う Skill は資料として読むだけにする。
- Git の読み取りや CLI の version/help 確認と、新規 AI セッションの起動を区別する。
- 実装開始は元の依頼、現在のモード、既存の承認に従う。レビュー完了を新たな実装承認と解釈しない。計画レビューは既存の pre-PR gate を置き換えない。

## prepare：依頼文を用意する

元の依頼と関連根拠を調査し、下の項目を短くまとめる。重要な判断理由を残し、事実・仮定・未確認を分ける。未解決の意図が計画を左右する場合は、先にユーザーと解消する。

```text
計画レビュー依頼（ユーザー編集可）
- 追加の懸念・重点:
- 今回変更した箇所:

作成元と返却先: この計画を作った元のセッションへ、結果と観察メモを返す。
元の依頼: Issue/要求の参照と、今回の要求・成功条件。
ユーザー追加の制約・対象外:
対象: repo/worktree の絶対パス、branch、HEAD、関連する未コミット差分と確認時点。
計画と検証方法:
主要な判断と理由:
根拠: 調査したファイル・行、公式資料、関連する実測とその版。
事実 / 仮定 / 未確認:
未解決事項:

あなたは新規セッションのレビュー専任。
元の依頼と関連根拠を調査して下記の結果形式で本文を返し、止めること。
結果形式: 重要な指摘 / 任意提案 / 調査した根拠・未確認の範囲 / 観察メモ。結果とメモを元の作成元へ返す。
コード・文書・公式資料・Skill の読み取り、Git の状態、CLI の version/help 確認は許可。
編集・実装・共有リソース変更・再委譲・新規 AI 起動・自動送信・監視は禁止。
既存の権限・承認を維持し、変更・委譲を伴う Skill は資料として読むだけにする。
```

依頼文を自身で元の要求・根拠・制約に照合してから提示する。ユーザーが相手の新規セッションへ渡す。既存セッションを別の役割へ切り替える場合は、その役割変更と維持する制約をユーザーの依頼文に明記する。

## review：受け取った計画をレビューする

1. 対象 repo、HEAD、関連差分と、元の依頼・主要な根拠を照合する。状態が変わっていれば、差異とレビューに影響する範囲を示す。旧 revision のレビューを現状にも有効だと断定しない。
2. 実質的な抜け・矛盾・失敗条件を優先する。指摘には根拠、影響、最小修正を添え、重要な指摘と任意提案を分ける。好みを修正必須にせず、指摘なしも認める。
3. 読めなかった参照や裏付け不足は、未確認の範囲・制限・必要な確認として報告する。推測で補わない。
4. 結果と観察メモをユーザーへ提示し、元の作成元セッションへの転送待ちで止める。

```text
重要な指摘: なし、または根拠・影響・最小修正。
任意提案: なし、または実質的な利益のある提案。
調査した根拠・未確認の範囲:
観察メモ: 役割、開示されたモデル、確認できたクライアント version、
使用ツール・権限、文脈不足・再説明、人の編集について把握できた事実。
返却先: 計画を作った元のセッション。結果とこのメモを一緒に返す。
```

## assess：元の作成元が採否を判断する

- 元の依頼・ユーザーの制約・現在の対象状態に照らして、各指摘を「採用」「不採用」「ユーザー判断待ち」に分け、理由を示す。自動的に採用せず、不採用も記録する。
- 採用する修正を計画へ反映し、修正版を要求・根拠・指摘への対応と照合する。重要な未解決事項はユーザーと解消する。
- 修正確認が必要なら、元の要求・制約、修正版、前回指摘と対応を含む依頼文を用意する。外部レビューは初回と必要な修正確認1回までとし、転送は再びユーザーに委ねる。任意提案だけで反復しない。
- 相手が利用不能・失敗なら、その段階を未実施と明示してセルフレビューする。これは通常の代替であり、相手を介した往復の成功とは記録しない。
- 採否・修正版・観察メモを本文で返す。実装は元の依頼・モード・承認の範囲でのみ開始する。

## 試行の記録

各段階で短い観察メモをチャットに残し、ユーザーが保持して結果と一緒に返す。実際の人の編集有無は、確認できなければ不明とする。

実タスクの記録には、両方向の役割・文脈の再利用、開示モデル／ツール／権限、有用な変更・不採用指摘、文脈欠落・再説明、人の転記負担、実装開始の承認と残る制約を要約する。生ログを保存せず、fixture・自動呼び出しと人が転送した往復を区別する。

## 読み込みと検証

Skill の一覧への表示と、入口・手順の本文読み込みを区別する。実際に読まれた path を確認し、project scope の fixture を user scope の実配置の証拠にしない。同名 Skill が先に見つかる環境では参照先を混同しない。

振る舞いは、prepare / review / assess、指摘なし、根拠不足、参照欠落、revision 変化、転送待ちを確認する。実ホームへの配置は別途承認し、対象の diff・dry-run、退避／復元、source の内容確認、適用後の読み返しに従う。
