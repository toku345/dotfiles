# Co-development

説明・議論・理解確認に使う時間も開発時間として扱う。まずは短い対話の手順を試す。hookによる強制や専用の進行コマンドは使わない。

## 進め方

1. **目的と現状を合わせる。** Issueと関連コードを調べ、全体の中で今回の変更が担う役割、実現したいこと、制約をAIの言葉で説明する。難しい・影響が大きい・戻しにくい判断は、選択肢と理由を示して確定前に相談する。必要なら小さく実装・検証して理解を深める進め方を提案する。
2. **計画後に理解を確認する。** 通常の計画・レビュー手順に従い、レビューの修正反映後、実装直前に重要な判断と期待する挙動を説明してミニクイズを一問出す。まだ存在しないコードの細部や、計画の暗記は問わない。プランモードでは、この確認と追加質問の時間をモード解除・実装承認の前に置く。
3. **回答へ応答してから待つ。** 根拠と照合して補足し、そこで一度返答を終える。追加質問・実装へ進む・保留の意向を確認し、ユーザーが明確に実装を依頼するか、実装開始を明示する承認操作をしてから着手する。クイズの正解や「理解しました」「LGTM」だけを着手の指示と解釈しない。合意した範囲内の編集・検証ごとに許可を取り直す必要はない。
4. **実装後にも理解を確認する。** AIが成果物を合意した意図・完了条件と照合し、検証結果と未確認事項を示す。重要な仕組みとテストの対応を説明し、具体例でミニクイズを一問出す。回答への補足で再び一度止まり、追加質問や次の操作の依頼を待つ。ユーザーが引き渡しに合意するまで、完了扱い・commit・PR作成を待つ。合意後の操作も既存の依頼・承認の範囲に従う。

## 説明と確認

- 実装中に想定外の制約や戻しにくい判断が現れたら、その判断を進める前に相談する。前提の変化・選択理由・合意を会話に残し、計画や理解確認を必要な範囲で更新する。

- 最初のミニクイズで、選択肢式／自由記述式の希望を聞く。以後は同じ形式を使い、途中変更も受け付ける。「分からないので説明してほしい」も選べるようにする。
- 全体像から短く説明し、質問に応じて深める。文章・具体例・図・コード追跡から、理解したい内容に合う形式を使う。
- 回答に詰まったら、質問の曖昧さや説明不足を見直し、説明方法を変える。同じ問いを正解まで繰り返さず、AIの説明が誤っている可能性も検討する。
- 一問の正解で全体の理解を認定しない。根拠との一致・食い違い・未確認を示し、理解できたかはユーザーが判断する。
- 疲れや理解の難しさがあれば、範囲縮小・中断・保留を選べるようにする。確認を見送った内容は未確認として残す。

最後に、理解に役立ったこと・負担だったこと・次に変えたいことを短く振り返る。初版ではこの体験を改善材料にする。後続Issueへ自動では進まない。
